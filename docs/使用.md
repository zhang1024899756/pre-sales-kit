# 使用

> 装好之后看这一篇。装的时候遇到问题，看 [安装](安装.md)。

---

## 速查

| 你现在的处境 | 命令 |
| --- | --- |
| 刚装完，手上什么都没有 | `kit init` |
| 想确认装对了 | `kit selfcheck` |
| 演示服务没起来 | `kit demo up` |
| 演示服务起了但页面没数据 | `kit demo down` → `kit seed` → `kit demo up` |
| 出门前 30 秒体检 | `kit doctor doctor.yaml` |
| 体检一片红，想让它自动修 | `kit doctor doctor.yaml --fix --yes` |
| 要一份能发给客户的报告 | `kit doctor doctor.yaml --html out/report.html` |
| 演示数据太假 / 停在三天前 | `kit seed -m points.yaml -o data/demo.db` |
| 客户问「支持 Oracle 11g 吗」 | `kit compat check --os "Windows Server 2016" --db "Oracle 11g"` |
| 要把兼容性贴进方案书 | `kit compat matrix --md out/matrix.md` |

## 一次完整的现场流程

工具是三个，但现场是一条线。下面这条线是我们自己在客户现场跑出来的顺序。

### 出差前一晚（T-1）

```bash
kit init                      # 1. 生成三份声明，按客户情况改
kit selfcheck                 # 2. 确认这台机器上的 kit 是对的版本

kit seed -m examples/points.yaml -o examples/data/demo.db \
    --start -24h --interval 5s          # 3. 生成物理合理的演示数据

kit demo up --db examples/data/demo.db  # 4. 起演示服务
kit doctor examples/doctor.yaml         # 5. 体检：应该在「数据」和「服务」上全绿
kit doctor examples/doctor.yaml --html out/T-1.html
```

第 5 步如果还有红项，**今晚修**，不要留到明天。

### 到现场、会前 10 分钟（T-0）

```bash
kit demo status                      # 一晚上过去，服务还活着吗
kit doctor examples/doctor.yaml      # 换了个网络、换了台机器，重新体检
kit demo open                        # 打开门户，确认首屏有数据
```

**顺序不要颠倒**：先 status 再 doctor。status 让你知道「昨晚还好、今早掉了」这个事实，
而 doctor 的回答会覆盖现状——先看清发生了什么，再决定要不要自动修。

### 客户问兼容性时（会中）

```bash
kit compat check --os "Windows Server 2016" --db "Oracle 11g"
```

结论行是**可以直接念出来的投标口径**：

```text
  结论
    ✗ 不支持  不应承诺：这个组合不受支持
    → 补丁依赖与 Oracle 11g 客户端冲突。应答为「不支持」，同时给出替代方案。
```

### 会后

```bash
kit doctor examples/doctor.yaml --html out/会后.html   # 留档
kit demo down                                          # 别让服务在客户机器上常驻
```

## kit init：生成可运行的示例

`kit doctor` / `kit seed` / `kit compat` 都要一份 YAML 才能工作。`kit init` 就是给你这三份。

```bash
kit init                      # 写到 ./examples/
kit init demo                 # 写到 ./demo/
kit init --only doctor.yaml   # 只导出其中一个
kit init --list               # 只看有哪些，不写文件
```

| 文件 | 是什么 | 后面谁用它 |
| --- | --- | --- |
| `doctor.yaml` | 11 项环境检查 + 修复命令 | `kit doctor` |
| `points.yaml` | 5 个点位、5 种物理模型 | `kit seed` |
| `matrix.yaml` | 3 个维度 + 3 个显式组合 | `kit compat` |

**关键行为：已存在的文件默认不覆盖。**

```text
$ kit init examples
    ✓ doctor.yaml       新建
```

```text
$ kit init examples         # 第二次跑，什么都不变
    · doctor.yaml       已是最新
```

如果你改过 `doctor.yaml`，再跑 `kit init` 会是：

```text
    ! doctor.yaml       保留原文件 · 已存在且内容不同，保留原文件（要覆盖加 --force）
```

这是故意的：现场机器上的 YAML 往往已经按客户情况改过，**那才是真的资产**。
确实想拿回最新样板时才加 `--force`，原文件会被备份成 `doctor.yaml.bak`。

导出之后它会直接把下一步命令打出来（带你的目录名），照着敲就行。

## kit selfcheck：装对了吗

```bash
kit selfcheck              # 终端报告
kit selfcheck --json       # 给脚本 / CI
kit selfcheck --dir out    # 顺便检查 out/ 这个目录能不能写报告
```

12 项检查，分四组：Python 与依赖（6 项）、安装记录与包内资源（3 项）、
命令行入口与编码（2 项）、输出目录可写（1 项）。每一项为什么重要、红了怎么修，见
[安装 · 装完先自检](安装.md#装完先自检)。

**退出码**：0 = 可以干活；1 = 有失败项。
警告（PATH 里没有 `kit`、控制台不是 UTF-8）不影响退出码，也不影响当天使用。

三种状态和别处一致：`✓` 通过、`!` 警告、`✗` 失败。

## kit demo：演示服务

0.2.0 新增：把「起一个能探测的服务」从手工拼命令变成一条命令。

```bash
kit demo up                                   # 起两个：门户 8080、报警通知 6379
kit demo up --only portal                     # 只起门户
kit demo up --db examples/data/demo.db        # 让门户读这份演示数据
kit demo up --service portal=8090             # 换端口（客户机器 8080 被占时）
kit demo status                               # 在跑吗？还是掉了 / 被占了
kit demo status --json                        # 给脚本
kit demo open                                 # 用浏览器打开门户
kit demo down                                 # 停掉
```

启动成功长这样：

```text
  启动
    ✓ 演示门户:8080         PID 30996 · 日志 demo-portal.log（启动器 32848 起的是子进程）
    ✓ 报警通知服务:6379     PID 34804 · 日志 demo-alarm.log

      打开看看：http://127.0.0.1:8080/   （或 kit demo open）
      停掉：kit demo down
```

> **那行「启动器 … 起的是子进程」是什么？**
> Windows 上 `python.exe` 有时是个应用商店别名 / 启动器，它自己不在监听，
> 真正监听的是它拉起的子进程。`kit demo` 记录的是**真正在监听的那个 PID**——
> 记错的话，`status` 会说「这不是 kit 起的」，`down` 也会杀错进程。

### 状态文件

`kit demo` 把「我起过什么」记在 `.kit/demo.json`（当前目录下）：

```json
{
  "version": 1,
  "saved": "2026-11-23T19:03:11+08:00",
  "services": [
    {"role": "portal", "port": 8080, "pid": 30996, "started": "2026-11-23T19:03:09+08:00", "db": "examples/data/demo.db"}
  ]
}
```

- 它只是记账。删掉不影响任何正在运行的进程，只是 `down` 会找不到它们。
- `--dir` 可以换位置：`kit demo status --dir examples` 读 `examples/.kit/demo.json`。
- 每个服务的输出在 `.kit/demo-<role>.log`，起不来时先看这个文件。

### 安全边界（重要）

`kit demo` 只碰**自己起的**进程。

| 情况 | 行为 |
| --- | --- |
| 端口空着 | 起服务，记下真实监听 PID |
| 端口已被别人占着 | **不动它**，报「端口被 PID x（进程名）占用，不是 kit 起的」 |
| `down` 时记录的 PID 还活着、端口也是它 | 停掉，清记录 |
| `down` 时端口上已经换成了别的进程 | 只清记录，**不动那个进程** |

客户机器上的 8080 可能跑着他们真实的服务。杀错一次的代价，比多敲一条命令大得多。

### 端口冲突怎么办

```text
    ✗ 演示门户:8080         127.0.0.1:8080 已被 PID 4211（javaw.exe）占用，没有动它，先腾出端口或换 --port
```

三选一：

```bash
kit demo up --service portal=8090     # 换端口（doctor.yaml 里对应的 port 也要跟着改）
kit doctor doctor.yaml --only 演示     # 先看清范围：到底哪几条检查受影响
kit doctor doctor.yaml                # 或按现状体检，从报告里读占用者是谁
```

想让 kit 替你把占端口的进程杀掉？它不会。那属于「改别人的机器」，
必须你自己确认那个进程是什么之后再动手。

## kit doctor：演示环境自检

```bash
kit doctor doctor.yaml                    # 体检（默认读当前目录的 doctor.yaml）
kit doctor doctor.yaml --fix              # 自动修能修的，修完逐项复检
kit doctor doctor.yaml --fix --yes        # 允许执行高风险修复（会重写数据库这类）
kit doctor doctor.yaml --html out/r.html  # 同时生成单文件报告
kit doctor doctor.yaml --only 演示 --only 数据   # 只跑这些标签的检查
kit doctor doctor.yaml --skip 显示        # 跳过
kit doctor doctor.yaml --strict           # 警告也算失败（退出码 1，给 CI 用）
kit doctor doctor.yaml --json             # 结构化输出
kit doctor --list-types                   # 有哪些检查类型（不需要声明文件）
```

### 声明文件

检查项**不写在代码里**，写在 YAML 里。加一条检查不用改一行 Python。

```yaml
version: 1
title: 客户现场演示环境自检
name: 华东某汽车零部件厂 · 产线能耗演示

defaults:
  timeout: 20        # 单条检查的兜底超时（秒）
  fix_wait: 2        # 修复后等多久再复检（秒）

checks:
  - id: portal-health            # 不写 id 会用「类型-序号」
    name: 门户健康检查            # 报告里显示的名字
    type: service                # 七类之一
    tags: [演示]                  # --only / --skip 用
    timeout: 5                   # 覆盖 defaults
    params:
      url: http://127.0.0.1:8080/health
      expect_status: 200
      body_contains: '"status": "ok"'   # 服务在，还要内容对
      retries: 2
    fix:
      action: start_service
      command: "{python} -m pre_sales_kit.demo --port 8080"
      wait: 2.5
      risk: low
```

顶层只有这几个键：`version` / `title` / `name` / `description` / `defaults` / `checks`。
**拼错一个键会直接报错**，不会被静默跳过——静默跳过的检查在现场等于没检查。

### 七类检查

| type | 查什么 | 参数 |
| --- | --- | --- |
| `port` | 端口在不在监听、该空的有没有被占 | `host` `port` `expect`（`listening` / `free`）`timeout` |
| `service` | HTTP 健康探测：状态码、响应体 | `url` `method` `expect_status` `body_contains` `headers` `timeout` `retries` `allow_redirects` |
| `data` | 记录数、时间新鲜度 | `path` `table` `time_column` `min_rows` `max_rows` `latest_within` `where` |
| `env` | 磁盘、时区、时钟偏移、控制台编码、证书 | `disk_path` `disk_min_free` `timezone` `clock_probe_url` `clock_max_skew` `encoding` `cert_path` `cert_host` `cert_port` `cert_min_days` `timeout` |
| `version` | 外部工具版本、Python 包版本 | `tools` `python_packages` `timeout` |
| `network` | 内网 / 外网 TCP 可达性 | `targets`（`name` / `host` / `port` / `expect`）`timeout` |
| `display` | 分辨率、浏览器 | `min_resolution` `browsers` |

路径类参数（`path`、`disk_path`）是**相对声明文件所在目录**的，不是相对你敲命令的目录。
这一点在换目录跑、或把声明放进子目录时最容易踩。

### 自动修复

`fix` 支持四种动作：

| action | 干什么 | 风险 |
| --- | --- | --- |
| `start_service` | 后台起一个命令，等 `wait` 秒 | 低 |
| `run_command` | 跑一条命令，看退出码 | 低 |
| `kill_port` | 杀掉占用端口的进程 | 低（会校验，不碰系统进程） |
| `reseed` | 重写演示数据库 | **高**，默认不执行，要 `--yes` |

`command` 里能用的占位符：`{python}`（当前解释器）、`{spec_dir}`（声明文件所在目录）、`{port}`（该检查的端口）。

**修复的关键设计：修完立刻复检。**「命令执行成功」和「问题解决」是两件事，报告里写的是复检结果：

```text
  修复
    ✓ 拉起服务 · 演示门户端口    已启动（PID 30996），等待 2.5s · 复检通过
    ! 重置演示数据 · 演示数据新鲜度  命令执行完成（退出码 0） · 复检仍未通过
```

`--fix` 最后还会做一轮**整体复检**：你修好了 A，没配 fix 的 B 可能自己就好了。

### 输出四形态

同一份结果的四种投影，措辞完全一致：

| 形态 | 什么时候用 |
| --- | --- |
| 终端红黄绿 | 当场判断 |
| `--html` 单文件 | 发给客户 / 留档。CSS 内嵌，无 CDN、无字体、无 JS，双击即开，断网可看 |
| `--json` | 脚本、CI |
| 退出码 | 0 无失败 / 1 有失败 / 2 声明或运行错误 |

警告不算失败；要严格就在 CI 里加 `--strict`。

## kit seed：物理上说得通的演示数据

随机的数据一定假，假在**物理约束**上：温度不会一秒跳 50 度，功率因数不会出现 0.3。

```bash
kit seed -m points.yaml -o demo.db                       # SQLite
kit seed -m points.yaml -o demo.csv                      # CSV（UTF-8 BOM，Excel 双击不乱码）
kit seed -m points.yaml -o - --format jsonl | head       # 管道
kit seed -m points.yaml -o demo.db --url http://host/api/ingest   # 直接打接口
kit seed -m points.yaml -o demo.db --html out/preview.html        # 预览图
kit seed -m points.yaml -o demo.db --inject-fault 14:20-14:35 \
    --fault-point 主轴电流 --fault-kind ramp --fault-magnitude 0.23
```

| 参数 | 说明 |
| --- | --- |
| `-m, --model` | 点位模型 YAML（默认 `points.yaml`） |
| `-o, --out` | `demo.db` / `demo.csv` / `demo.jsonl` / `-`（标准输出） |
| `-f, --format` | `sqlite` / `csv` / `jsonl` / `api`，默认按扩展名推断 |
| `--start` `--end` | `now` / `-24h` / `2026-11-23 08:00` |
| `--interval` | `5s` / `1m` / `500ms` |
| `--seed` | 随机种子：同参数永远同一份数据 |
| `--url` `--header` `--batch-size` `--timeout` `--dry-run` | `--format api` 用 |
| `--inject-fault` `--fault-point` `--fault-kind` `--fault-magnitude` | 异常注入 |
| `--verify/--no-verify` | 生成后做物理自检（默认开） |
| `--list-models` | 列出五种模型及参数 |

### 点位 YAML

```yaml
version: 1
name: 产线能耗与设备监控 · 演示点位
interval: 5s

points:
  - name: 主轴温度
    unit: ℃
    model: thermal          # 五种之一
    baseline: 45
    range: [20, 85]         # 硬约束：生成完一个点都不越界
    decimals: 1
    params:
      tau_heat: 240
      tau_cool: 600         # 降温比升温慢：真实设备就是这样
    faults:                 # 也可以写在点位里，替代 --inject-fault
      - {kind: ramp, from: "14:20", to: "14:35", magnitude: 0.23}
```

点位字段：`name` `model` `unit` `range` `baseline` `decimals` `params` `faults`；
`faults` 里的字段：`kind` `from` `to` `magnitude` `note`。未知字段直接报错。

### 五种模型

| model | 用在什么量 | 关键参数（括号里是默认值） |
| --- | --- | --- |
| `thermal` | 温度、电机绕组 | `tau_heat`(240) `tau_cool`(600) `ambient`(24) `drift`(1.2) `noise`(0.08) |
| `load_step` | 电流、功率 | `idle` `levels` `dwell_min`(45) `dwell_max`(240) `inrush`(1.35) `inrush_tau`(1.5) `noise`(0.12) |
| `random_walk` | 功率因数、精度指标 | `start` `theta`(0.35) `sigma` `noise` |
| `triangle` | 液位、压力 | `period`(900) `duty`(0.55) `low` `high` `noise` |
| `counter` | 产量、件数 | `rate`(12) `downtime_per_hour`(0.4) `downtime_seconds`(90) `reset_hours`([8,20]) |

`kit seed --list-models` 能随时查完整说明。

### 自检

生成完会自己验一遍，逐项报告：

```text
  点位         模型          实际范围          单步最大   自检
  主轴温度     thermal       42.4 ~ 47.2 ℃     0.3        通过
  主轴电流     load_step     9.8 ~ 21.41 A     11.22      通过
  功率因数     random_walk   0.874 ~ 0.922     0.007      通过
```

四项检查：越界数、单步最大跳变、计数是否回退、是否被 `decimals` 四舍五入成一条直线。
自检没过退出码是 **3**（数据已经落盘了，但你知道它不合格）。

### 异常注入

注入的是**物理上仍然成立**的异常——是「主轴电流在 14:20 之后缓升 23% 量程」，
不是「突然跳到量程上限」。这样告警演示才经得起客户追问。

四种形态：`ramp`（缓升）、`spike`（尖峰）、`dropout`（卡死/掉线）、`drift`（漂移）。
时间窗可以只写时分（`14:20-14:35`，落在数据集当天），也可以写完整日期。

## kit compat：兼容性一条命令

```bash
kit compat check --os "Windows Server 2016" --db "Oracle 11g"
kit compat check --os centos --db 达梦 --json
kit compat check --set cpu=鲲鹏920 --set db=达梦DM8       # 任意维度
kit compat matrix                                        # 打印整张矩阵
kit compat matrix --md out/matrix.md --brand "XX 科技"    # 贴进方案书
kit compat matrix --html out/matrix.html                 # 单文件表格
```

### 矩阵 YAML

```yaml
version: 1
product: 产线能耗与设备监控平台 v3.2
updated: "2025-11-20"
labels:                      # 维度显示名，不写就用键名
  os: 操作系统
  db: 数据库

os:                          # 除保留字段外，每个顶层键都是一个维度
  - { name: Windows Server 2016, status: partial, note: 需补丁 KB4532945 }
  - { name: Windows Server 2019, status: full }
db:
  - { name: Oracle 11g, status: unsupported, note: 建议升级至 19c }

combinations:                # 显式组合优先于单维度推断
  - { os: Windows Server 2016, db: Oracle 11g, status: unsupported, note: 补丁依赖冲突 }
```

保留字段：`version` `product` `updated` `notes` `description` `labels` `combinations`。
其他键自动成为维度，**加维度不用改代码**。

状态词：`full`（支持）/ `partial`（有条件）/ `unsupported`（不支持）/ `unknown`（未验证）。

### 匹配是渐进的，而且不替你认领

精确 → 包含 → 前缀 → 近似。`centos` 能命中 `CentOS 7.9`，但**近似匹配会在结论里标出来**。
维度没收录、值不在矩阵里，都不会被猜成「支持」。

### 结论与退出码

```text
  维度     查询值                结论     说明
  操作系统  Windows Server 2016   部分支持  需补丁 KB4532945
  数据库    Oracle 11g             不支持    建议升级至 19c

  结论
    ✗ 不支持  不应承诺：这个组合不受支持
    → 补丁依赖与 Oracle 11g 客户端冲突。应答为「不支持」，同时给出替代方案。
```

| 退出码 | 含义 |
| --- | --- |
| 0 | 完全支持 |
| 1 | 不支持 |
| 3 | 有条件支持 |
| 4 | 维度未收录，需要确认 |

## 脚本化

三个命令都能进脚本和 CI。形状是一样的：**`--json` 给机器，退出码给判断**。

```bash
kit selfcheck --json                  # 0 / 1
kit doctor d.yaml --json              # 0 / 1 / 2
kit seed -m p.yaml -o d.db            # 0 / 2 / 3（3 = 自检没过）
kit compat check --os ... --db ...    # 0 / 1 / 3 / 4
kit demo status --json                # 0
```

```bash
#!/usr/bin/env bash
set -euo pipefail
kit demo up --db examples/data/demo.db --wait 8 || true
if kit doctor examples/doctor.yaml --json > out/doctor.json; then
  echo "环境 OK"
else
  echo "环境有问题，看 out/doctor.json"
  jq -r '.checks[] | select(.status=="fail") | "  \(.name): \(.detail)"' out/doctor.json
```

## 排错

| 症状 | 先看 | 处理 |
| --- | --- | --- |
| 找不到声明文件 | 路径对不对 | `kit init` 生成，或写绝对路径 |
| `checks 是空的` | YAML 缩进 | `checks:` 下面每项要以 `- ` 开头 |
| 拼错的键报错 | 报错里会给出位置 | 按提示改；不确定的键对照本文档的表格 |
| 检查总是超时 | 是不是写了外网地址 | 加大 `timeout`，或 `--skip` 掉网络类检查 |
| `--fix` 后仍然红 | 复检结果才是真的 | 看「修复」段里的「复检仍未通过」，再按提示查 |
| 数据检查报「停在三天前」 | 生成时间 | `kit seed ... --start -24h` 重新生成 |
| seed 自检报「被四舍五入成直线」 | `decimals` 太小 | 增大 `decimals`，或换变化更明显的模型 |
| compat 报「维度未收录」 | 矩阵里有没有这个维度 | 补进 YAML；或接受退出码 4 去人工确认 |
| `kit demo status` 说不是 kit 起的 | 端口被别的进程占了 | 换端口：`kit demo up --service portal=8090` |
| `kit demo up` 起来的服务立刻退出 | `.kit/demo-<role>.log` | 看日志最后几行；常见是端口被占或 `--db` 路径不可写 |
| 报告里的中文是方块 | 终端字体 | HTML 用系统字体栈，浏览器打开正常即可；终端显示问题与 HTML 无关 |
