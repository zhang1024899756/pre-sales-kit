# 安装

> 这份文档只解决一件事：**从零到 `kit selfcheck` 全绿**。
> 装好之后每个命令怎么用，看 [使用](使用.md)。

---

## 先挑一种装法

| 你的情况 | 用这个 | 一条命令 |
| --- | --- | --- |
| 能上外网，只想用 | pipx | `pipx install pre-sales-kit` |
| 机器上有 uv | uv tool | `uv tool install pre-sales-kit` |
| 现场机器拿不到外网 | 本地 wheel | [离线 / 内网安装](#离线--内网安装) |
| 要改代码、跑测试 | 源码 editable | [从源码装](#从源码装要改代码时) |

> **现状说明**：pre-sales-kit 0.2.0 还没有发布到 PyPI。
> 在那之前前两种方式会失败（`No matching distribution found`），请用「本地 wheel」或「从源码」。
> 发布之后，第一节才是最短路径。

需要 Python **3.11 或 3.12**。3.10 及更早不行（用了 `X | None` 这类语法和 3.11 的标准库特性）。

---

## 从 PyPI 装（发布之后最短的一条）

**pipx** 是最省事的：它给每个命令行工具建独立环境，装上之后 `kit` 直接进 PATH，
也不会和你项目里的依赖打架。

```bash
pipx install pre-sales-kit
kit --version          # pre-sales-kit 0.2.0
```

**uv tool** 同理，适合已经用 uv 的人：

```bash
uv tool install pre-sales-kit
```

**不想装额外工具**，用 pip 装到当前环境（注意会进这个环境的依赖）：

```bash
python -m pip install pre-sales-kit
```

三个入口是等价的：

| 入口 | 什么时候用 |
| --- | --- |
| `kit ...` | 正常情况 |
| `pskit ...` | `kit` 这个名字被别的工具占了（少见） |
| `python -m pre_sales_kit ...` | PATH 没配好，但 Python 能找到包 |

## 本地 wheel（没发布、或现场没外网）

wheel 是**一个文件**，里面已经有全部代码、报告模板和示例 YAML。拿到它的方式有两种。

**A. 从源码构建**（要一台有构建工具的机器，构建过程本身不需要联网）：

```bash
git clone https://github.com/arvinzxy/pre-sales-kit
cd pre-sales-kit
python -m pip install hatchling          # 只需一次
python -m hatchling build -t wheel       # 产物在 dist/
ls dist/
# pre_sales_kit-0.2.0-py3-none-any.whl
```

**B. 直接从别人手上拷** `dist/pre_sales_kit-0.2.0-py3-none-any.whl`，跳过构建。

然后装：

```bash
python -m pip install dist/pre_sales_kit-0.2.0-py3-none-any.whl
kit selfcheck
```

## 从源码装（要改代码时）

```bash
git clone https://github.com/arvinzxy/pre-sales-kit
cd pre-sales-kit
python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -e ".[dev]"     # -e：改代码立刻生效；[dev]：pytest / ruff / mypy
kit selfcheck
```

有 uv 的话两条命令搞定：

```bash
uv venv && uv pip install -e ".[dev]"
```

`[dev]` 装的是开发工具，日常使用不需要。

## 装完先自检

不要跳过这一步。现场最耗时间的失败不是工具报错，而是**命令指向了另一份旧安装**：
它照样能跑，只是行为跟文档对不上。

```bash
kit selfcheck
```

装好的样子：

每一项在查什么：

| 检查 | 说明 | 红了怎么办 |
| --- | --- | --- |
| Python 版本 | 低于 3.11 直接起不来 | 换 3.11+ 重装（见下面的排错表） |
| 依赖 ×5 | typer / rich / pyyaml / jinja2 / tzdata | `pip install --force-reinstall pre-sales-kit` |
| 安装记录 | `pip` 记的版本 vs 代码里的版本 | 两者不一致说明装了一半，重装 |
| 报告模板 | 4 个 Jinja2 模板 | 包不完整，`--html` 会失败；重装 |
| 示例文件 | 3 份 YAML | `kit init` 会失败；重装 |
| 命令行入口 | `kit` 在不在 PATH | 只是警告：仍可用 `python -m pre_sales_kit` |
| 控制台编码 | 中文会不会显示成问号 | 只是警告；`chcp 65001` |
| 输出目录可写 | 报告和演示数据要落盘 | 换目录：`kit selfcheck --dir out` |

**退出码**：0 = 可以干活；1 = 有失败项，先修。警告不影响退出码，也不影响当天使用。

## 离线 / 内网安装

客户现场常见的组合是：机器没外网、没有 pip 缓存、Python 还是别人装的。
做法是**在有网的机器上把 wheel 全下齐**，拷过去一次装完。

```bash
# 1. 有网的机器（Windows 就用 Windows 下，和现场尽量同 OS / 同 Python）
python -m pip download pre-sales-kit -d wheelhouse
#    还没发布时，先构建再补依赖：
python -m hatchling build -t wheel -d wheelhouse
python -m pip download -d wheelhouse \
    "typer>=0.15" "rich>=13.9" "pyyaml>=6.0" "jinja2>=3.1" "tzdata>=2024.1"

# 2. 整个 wheelhouse 目录拷到 U 盘，带到现场

# 3. 现场机器上，离线安装
python -m pip install --no-index --find-links wheelhouse pre-sales-kit
kit selfcheck
```

几个要点：

- `--no-index` 是必须的，否则 pip 仍会尝试联网并卡住（表现是「Install 之后一动不动」）。
- 当前依赖全是纯 Python 包，跨平台一般没问题；但**同 OS 同 Python 版本下载最稳**。
- 如果现场机器上 `pip` 也没有，先用 `python -m ensurepip --upgrade` 把它捞出来。
- 不想污染现场机器的话，可以用 `--target` 装到某个目录，再用 `python -m pre_sales_kit` 跑。

## 升级、降级、卸载

```bash
# pipx
pipx upgrade pre-sales-kit
pipx uninstall pre-sales-kit

# uv tool
uv tool upgrade pre-sales-kit
uv tool uninstall pre-sales-kit

# venv / 全局 pip
pip install -U pre-sales-kit
pip install pre-sales-kit==0.2.0    # 降级：装回指定版本
pip uninstall pre-sales-kit
```

**两个版本同时存在**（很容易发生：pipx 装了一份、项目 venv 里又装了一份）时：

```bash
kit --version                        # 实际会执行的那份
python -m pre_sales_kit --version    # 当前 Python 环境里的那份
where kit                            # Windows：列出所有 kit
which -a kit                         # macOS / Linux
```

两个版本号不一致就说明 PATH 里先命中的是另一份。要么卸载旧的，要么用绝对路径调。

## 装不上：按症状查

| 症状 | 原因 | 先确认 | 处理 |
| --- | --- | --- | --- |
| `kit: command not found` | 脚本目录不在 PATH | `python -c "import sysconfig;print(sysconfig.get_path('scripts'))"` | 把这个目录加进 PATH；临时可用 `python -m pre_sales_kit` |
| `No matching distribution found` | 0.2.0 还没发到 PyPI | `pip index versions pre-sales-kit` | 用本地 wheel 或从源码装 |
| `Requires-Python >=3.11` | Python 太旧 | `python -V` | 装 3.11+ 后 `pipx install --python 3.11 pre-sales-kit` |
| 安装过程中长时间无输出 | 默认索引不通（内网 / 代理 / 镜像未配） | `pip config list` | 加 `-i https://pypi.tuna.tsinghua.edu.cn/simple`，或走离线 wheelhouse |
| `kit` 能跑，但行为和文档不一样 | PATH 上是旧版本 | 上面「两个版本同时存在」 | 卸载旧的或 `--force-reinstall` |
| `kit init` 报示例文件缺失 | 包不完整（手工拷了部分文件 / 老 wheel） | `kit selfcheck` 看「示例文件」那行 | 用同一份 wheel 重装 |
| 中文显示成 `???` | 控制台代码页不是 UTF-8 | `chcp` | `chcp 65001`；或 `set PYTHONUTF8=1`。生成的 HTML 不受影响 |
| `--html` 写不出来 | 目录不可写 / 被杀毒软件拦 | `kit selfcheck --dir out` | 换目录；把该目录加进杀软白名单 |

## 它到底装了什么（边界）

装的是一个纯 Python 包，加上两个命令行入口。**没有**常驻服务、开机启动、注册表项、驱动。

| 位置 | 内容 | 能不能删 |
| --- | --- | --- |
| `.../site-packages/pre_sales_kit/` | 代码、报告模板、示例 YAML | 卸载时一起删 |
| `.../Scripts/kit.exe`、`pskit.exe` | 命令入口 | 同上 |
| `examples/`（当前目录） | `kit init` 生成的声明文件 | 随便删，随时能重新生成 |
| `.kit/`（当前目录） | `kit demo` 的状态与日志 | `kit demo down` 之后可删 |
| `out/`（当前目录） | 生成的报告 | 随便删 |

网络方面：工具本身不联网。只有当你**在 YAML 里写了 URL**（`service` 检查、`network` 探针、`seed --url` 推送）时才会发请求——
发往哪里，你的声明文件里写得清清楚楚。
